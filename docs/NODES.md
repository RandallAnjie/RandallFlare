# 节点能力、调度与排空

RandallFlare 没有中心调度器。节点策略与 Worker 部署约束都属于管理员签名、带
哈希前序的不可变资源；任意节点收到新版本后都能独立得出同一个落位结果。节点
本身只通过集群加密 Gossip 上报在线状态和本机能力，不存在可被单点篡改的节点表。

## 能力标签

节点会自动发布以下系统标签：

| 标签 | 含义 |
| --- | --- |
| `public` | 节点开放公网入口，并可加入轮转 DNS |
| `build` | 节点启用了 Git 构建执行器 |
| `rclone` | 节点同时配置了 rclone 程序与本地凭据文件 |
| `email` | 节点显式启用了可选邮件角色 |

管理员还可在“节点与调度”页面为节点签名自定义标签，例如 `gpu`、
`high-memory`。区域 `eu-west` 会额外形成 `region-eu-west` 标签。标签只允许
小写字母、数字与连字符；自定义标签不应包含供应商密码、机器地址或其他机密。

## Worker 部署约束

在 `rf.json` 中填写全部必须满足的标签：

```json
{
  "name": "image-worker",
  "main": "index.js",
  "required_tags": ["region-eu-west", "gpu"]
}
```

也可以在 Worker 的“设置 → 运行时与调度”中逐行编辑。约束会写入签名清单的
内部元数据，普通环境变量接口与 workerd 运行环境都不会暴露它。

每个节点只启动自己满足全部标签的 Worker。静态资源 Worker 虽然已在内容块层面
复制到各节点，也只有合格节点会被报告为 `ready`。公网请求如果先抵达不合格或
尚未就绪的节点，入口会从实时 Gossip 状态中选择一个合格实例，经
XChaCha20-Poly1305 集群通道转发完整请求。目标节点再次检查 Worker 名称、清单
版本、预览资源版本、签名策略和本地就绪状态；陈旧路由不能降级成错误版本。

选择采用稳定的 rendezvous 分数，同一 Worker 会优先命中同一合格节点，同时在
节点故障时自然切换。Durable Object 不使用这条无状态转发路径：首次建立其 D1
微仲裁组时只选择满足约束的节点，之后所有入口仍转发到经过 epoch 栅栏保护的唯一
所有者。

## 排空与停用

- **排空公网流量**：节点停止注册或保留轮转 A 记录，但现有进程与内部副本继续
  工作；已经抵达此节点的请求仍可安全转发。用于计划维护前逐步移走流量。
- **停用调度**：普通 Worker 和预览不再在该节点运行，节点也退出公网 DNS 集合；
  数据副本、Gossip 与管理接口保留，以便恢复。
- 为防止已确认的 Durable Object 状态失去唯一所有者，策略在所有者变更期间不会
  粗暴杀死当前 epoch 的进程。新建 DO 的仲裁组已遵守最新标签；维护已有 DO 节点
  时，应先确认控制台显示的新所有者已经接管，再关闭旧节点。

DNS 清理由带租约的单例任务完成，并保留网络分区保护：看不到任何其他公网成员的
节点不会擅自删除记录。策略变更同时触发运行状态 Gossip，因此资产型 Worker 也会
立即从 `ready` 切换为 `not_placed`。

## 安全操作顺序

1. 在“节点与调度”选择目标节点，填写原因并先启用“排空公网流量”。
2. 在管理员设备使用页面显示的一次性代码批准确切策略；节点和浏览器都不会接触
   管理员私钥。
3. 等待 DNS TTL，并确认 Worker 分发视图中其他节点均为 `ready` 或 `running`。
4. 如需停止计算负载，再签名“停用调度”；保留 Peer API 与 Gossip 直至迁移完成。
5. 维护结束后先取消停用，确认实例就绪，再取消排空。

多节点生产环境应至少保留三个满足关键 Worker 标签的独立节点，否则 D1、Workflow
与 Durable Object 无法提供多数派容错。
